### The learner-requested bug investigation (highest-value segment so far)

The learner asked whether the failing sample code was *deliberately* broken or a bug. Ran a
4-round controlled experiment; kept the scripts at
`phases/14-agent-engineering/04-tree-of-thoughts-lats/code/experiment_value_fn.py` and
`diagnose_pruning.py`.

1. Shipped code fails in both modes. ToT returns `6*4=24, 4-1=3, 24+3=27` (wrong, 152 expansions);
   LATS returns a fake leaf `(24,4)` (286 expansions).
2. **Fix #1 (real bug):** `_all_leaves` treats "no children" as a leaf while `expand()` uses
   `len(state) < 2`. A never-expanded `(24,4)` node was returned as a finished leaf. Confirmed —
   after the fix LATS falls back to root `(6,4,4,1)`.
3. **My first diagnosis was wrong.** I claimed the biased `value()` was the root cause. The
   `leftover` penalty I added is a *constant within a BFS level* (all depth-1 nodes have
   `len(state)==3` → same `-0.4` shift), so the top-8 set was byte-identical. The fix was inert.
4. **The binding constraint is the search shape, not the scorer.** Widening the BFS beam 8→12→16→24
   changed nothing at all: `(24,4,1)` scores a perfect 0.0 and outranks the real solution paths
   (`-0.17`, `-0.19`) at every width. MCTS at 400 iterations *did* solve it
   (`6+1=7, 7*4=28, 28-4=24`) because UCT's exploration term deflates the over-visited branch.
   Two genuine solutions exist: `6+1=7, 7*4=28, 28-4=24` and `6-1=5, 5*4=20, 20+4=24`.

Teaching payoff to reuse: this is a *better* lesson than a bug-free sample. It makes "search
optimises whatever you score" reproducible, and it shows the UCT exploration term is a
bias-compensation mechanism, not just an explore/exploit knob. It also demonstrates the honest
research loop — I revised my own conclusion three times on the evidence.
